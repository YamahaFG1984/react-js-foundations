原书清单在做什么

第一个例子用两个 <script> 从 CDN 引入 react 和 react-dom，然后手写 React.createElement—— 故意不用 JSX，好让你看见 JSX 底下是什么：

// chapter01/HelloWorld.js —— 原书写法
class HelloWorld extends React.Component {
  constructor(props) {
    super(props);
    this.state = { personName: "World" };

  render() {

三个已经变了的细节

① 不用再写 import React from "react"——React 17 起的新 JSX transform 由编译器自动引入 jsx()。 ② createRoot 返回的 root 可以 .unmount()，同一个页面能挂多个 root。 ③ 服务端渲染出来的页面用 hydrateRoot，不是 createRoot。

小结
  • JSX 是语法糖，编译后就是函数调用；React Element 是普通不可变对象。
  • Fiber 是运行时的可变结构，Hooks 的数据就存在这里。
  • Vue 模板同样被编译，两者都没有"运行时解析字符串模板"这回事。
补 A · 书里没有

key 与协调算法

上一节的管线停在"协调算出差异"。这一节讲它怎么算——以及为什么 key 写错会让输入框里的内容整体错位一格。

三条规则

React 拿到新旧两棵 Element 树后，不做通用的树 diff（那是 O(n³)），而是靠三条假设把复杂度降到 O(n)：

  1. 只比同一层。跨层级移动节点不会被识别成"移动"，只会是"这边删掉、那边新建"。
  2. 同一位置上 type 变了，整棵子树扔掉重建。div 换成 span、Counter 换成 Timer，里面所有 DOM 和 state 一律销毁。
  3. type 相同时，按 key 配对。没写 key 就按下标配对。配上了就复用那个节点——包括它的 DOM 和 state。

第三条是全部麻烦的来源。看一个具体场景：

什么时候下标当 key 才是安全的

三个条件同时满足：列表永不重排、只在末尾增删、列表项自身没有状态（纯展示文本）。 留言板按时间追加就符合——所以第 8 章那个例子用 key={i} 没问题。 但只要以后可能加上"删除"或"置顶"，它就会立刻变成 bug。默认给稳定 id，成本低得多。

规则二的另一面：条件渲染会意外销毁子树

React · 同一个组件，被包了一层就重建
// ❌ 两个分支里 <Input/> 所在位置的 type 不同
//    切换 fancy 时，输入框内容会被清空
{fancy
  ? <div className="fancy"><Input /></div>
  : <Input />}

// ✅ 保持结构一致，只换 class —— 节点被复用，内容保留
<div className={fancy ? "fancy" : ""}>
  <Input />
</div>

// 同理，这两个写法的行为完全不同：

// type 相同 → 节点被复用，count 保留
{isA ? <Counter /> : <Counter />}

// key 不同 → 卸载重建，count 归零
{isA ? <Counter key="a" /> : <Counter key="b" />}
Vue · 完全一样的规则
<template>
  <!-- ❌ 两个分支结构不同，切换时 input 内容丢失 -->
  <div v-if="fancy" class="fancy"><Input /></div>
  <Input v-else />

  <!-- ✅ 结构一致 -->
  <div :class="{ fancy }"><Input /></div>

  <!-- Vue 里 v-if / v-else 的同类型元素默认会复用， -->
  <!-- 想强制重建就给不同的 key -->
  <input v-if="isEmail" key="email" placeholder="邮箱" />
  <input v-else key="phone" placeholder="手机号" />
</template>
小结
  • 协调只比同层；type 变了就整棵子树重建；type 相同按 key 配对。
  • key 是数据的身份证：同列表内唯一、跨渲染稳定。默认用后端 id 或 crypto.randomUUID()。
  • 下标当 key 只在"永不重排 + 只在末尾增删 + 项无状态"时安全。
  • 条件渲染时保持两个分支的结构一致，否则子树会被无谓地销毁重建。
Chapter 03

JSX 不是模板

花括号里是 JavaScript 表达式，不是模板语法。理解这一条，本章所有"技巧"都变成常识。

chapter03/ConditionalWelcome{,2,3}.js · FragmentExample{1,2}.js · ImmediateInvoke.js · SearchBox/

原书清单在做什么

三个 ConditionalWelcome 展示了条件渲染的三种写法，ImmediateInvoke.js 甚至在 JSX 里塞了个立即执行函数。 它们背后是同一条规则：{} 里必须能求值成一个值，所以 if 语句不行，三元和 && 行。

条件渲染的三种写法

&& 的经典陷阱

{count && <Badge/>} 在 count === 0 时会把 0 渲染到页面上——因为 0 && x 求值为 0，而 React 会渲染数字。 要么写 {count > 0 && …}，要么写 {count ? … : null}。Vue 的 v-if="count" 不会有这个问题，因为它只判真假、不输出判断结果。

小结
  • {} 里只能放表达式；需要语句就在 return 之前写，或者抽成函数。
  • <X/> 产生一个描述对象，不等于执行了 X。
  • Fragment（<>…</>）解决的是"必须单根"的限制；Vue 3 的模板本来就支持多根节点。

class 与函数，写法之外的差别

原书把同一个待办列表写了两遍（ToDoClass.js / ToDoFunction.js）。除了少打很多字，函数组件真正的区别在于： 它没有 this，所以不需要 bind；它每次渲染都是一次全新的函数调用。 原书 UnboundFunction.js 与 BoundFunction.js 演示的那个 this 陷阱，在函数组件里根本不存在。

React 19 · ToDo.tsx（函数组件 + TS）
import { useState, type FormEvent } from "react";

type Todo = { id: string; text: string };

export default function ToDo() {
  const [item, setItem] = useState("");
  const [list, setList] = useState<Todo[]>([]);

  function handleSubmit(e: FormEvent) {
    e.preventDefault();
    if (!item.trim()) return;
    // 造新数组，并给每条数据一个稳定 id（为什么：见「补 A」）
    setList([...list, { id: crypto.randomUUID(), text: item }]);
    setItem("");
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={item}
        onChange={(e) => setItem(e.target.value)}
        placeholder="what to do?"
      />
      <button type="submit">Add</button>
      {list.map((todo) => (
        <p key={todo.id}>{todo.text}</p>
      ))}
    </form>
  );
}
Vue 3 · ToDo.vue
<script setup lang="ts">
import { ref } from "vue";

const item = ref("");
const list = ref<{ id: string; text: string }[]>([]);

function handleSubmit() {
  if (!item.value.trim()) return;
  // 可以直接改；key 同样要用稳定 id
  list.value.push({ id: crypto.randomUUID(), text: item.value });
  item.value = "";
}
</script>

<template>
  <form @submit.prevent="handleSubmit">
    <input v-model="item" placeholder="what to do?" />
    <button type="submit">Add</button>
    <p v-for="todo in list" :key="todo.id">{{ todo.text }}</p>
  </form>
</template>
第一个真正的分歧：能不能改

Vue 那边 list.value.push(...) 直接生效——因为数组被 Proxy 包过，改动会被拦截并通知订阅者。 React 这边 必须造一个新数组：setList([...list, newTodo])。 如果你写 list.push(newTodo); setList(list)，React 拿到的是同一个引用，判定"没变"，界面不会更新。 这不是 React 笨，而是它靠"引用是否改变"来判断，代价换来的是可预测性——数据永远不会在你没注意的地方被偷偷改掉。

重渲染是会传染的

原书用 PureComponent 和 React.memo 处理这个问题。先看清楚问题本身：

Vue 侧没有对应物

Vue 组件的更新由依赖追踪驱动：Child 只有在它读过的响应式数据变化时才重新渲染。 所以 Vue 里没有 memo、没有 useCallback，也很少有人讨论"重渲染传播"。 代价是你要记得把状态放进 ref/reactive，否则它根本不在追踪范围内。

顺带一提：LeakyCounter

原书 LeakyCounter.js 在 componentDidMount 里开了个 setInterval 却没清理，组件卸载后定时器还在跑并调用 setState； NoLeakCounter.js 补上 componentWillUnmount 修好了它。函数组件里这对生命周期合并成了 useEffect 的返回值， 详见 第 11 章的时序图。

小结
  • 写新代码不用 class；this 绑定问题随之消失。
  • React 的状态更新必须产生新引用；Vue 可以就地修改。
  • children 只是一个 prop，因此组合能力天然存在，不需要插槽语法。
  • memo 依赖 props 引用稳定；React Compiler 正在把这件事自动化。

PropTypes 已经没用了

原书 WelcomeMessage.js、Contact.js、DisplayPrimaryColors.js 大量使用 prop-types。 React 19 已经移除了对 Component.propTypes 的读取——写了不报错，但也不校验。 对照表：PropTypes.string → string；.isRequired → 去掉 ?； PropTypes.oneOf(["red","green"]) → "red" | "green"； PropTypes.node → ReactNode；PropTypes.element → ReactElement； PropTypes.func → 写出完整函数签名。类型检查从运行时挪到了编译期，而且更准。

原书的 SearchBox（第 3、8 章都出现）是最小的"状态提升"样本：两个兄弟组件要共享一个搜索词， 于是搜索词被提到它们最近的公共父级。

规则三：状态是这一次渲染的快照

  count.value++;          // 直接 +2，无需特殊写法

  console.log(count.value);   // 2 —— 读的是容器当前值
  console.log(document.querySelector("button")?.textContent);
  // 仍是旧的 —— DOM 还没更新

  await nextTick();       // 等这一轮更新刷进 DOM
  console.log(document.querySelector("button")?.textContent); // "2"
}
</script>

<template>
  <button @click="incrementTwice">{{ count }}</button>
</template>
两边都有"异步"，但异步的东西不同

Vue 里 数据是同步的，DOM 更新是异步的（所以有 nextTick）。 React 里 数据本身在本次渲染中就不会变（快照），DOM 更新自然也是之后的事。 把这两句话记牢，90% 的"为什么我拿到的是旧值"就解释清楚了。

不可变更新的常用写法

原书 RemindersClass/App.js 里有一段典型的"改数组中某一项"：

// 改第 index 项的 isComplete —— React 必须造新数组、新对象
setReminders(reminders.map((r, i) =>
  i === index ? { ...r, isComplete } : r
));

// 增：setReminders([...reminders, item]);
// 删：setReminders(reminders.filter((_, i) => i !== index));
// 排序：setReminders([...reminders].sort(cmp));   // 先复制，sort 会改原数组

// 结构很深时，用 useReducer 或者 immer 的 produce()，
// 别手写五层展开运算符。

Vue 对应写法就是 reminders.value[index].isComplete = isComplete——一行。 这是两边最直观的体验差异，也是各自设计取舍最集中的地方。

小结
  • props 只读；默认值写在解构里；类型交给 TypeScript。
  • 状态提升到最近公共父级：数据下行，事件上行。
  • state 是本次渲染的快照：基于旧值算新值时用 setState(prev => …)。
  • 同一事件内的多次 setState 会批处理，只重渲染一次。
  • React 需要不可变更新，Vue 可以就地修改——这是两者所有差异的根。
补 B · 书里没有

状态住在树的哪个位置

上一节说 state 是"这次渲染的快照"。那这份数据究竟存在哪？答案不是"存在组件里"——是存在树中的那个位置上。

你写的 Counter 只是一个函数，它被调用一百次就产生一百份独立的 state。区分它们的不是函数本身， 而是 React 在树里给它安排的位置：父节点 + 在同层中的次序 + key。位置不变，state 就一直在；位置一变，state 就没了。

React · 用 key 重置，而不是用 effect 同步
// ❌ 常见但错误：用 effect 把 props 同步进 state
function ProfileForm({ userId, initialName }: Props) {
  const [name, setName] = useState(initialName);

  useEffect(() => {
    setName(initialName);      // 换用户时重置
  }, [userId]);                // 会多渲染一次，还容易漏字段

  return <input value={name}
    onChange={(e) => setName(e.target.value)} />;
}

// ✅ 让 React 自己重建：换 key 即可
function ProfileForm({ initialName }: { initialName: string }) {
  const [name, setName] = useState(initialName);
  return <input value={name}
    onChange={(e) => setName(e.target.value)} />;
}

// 父组件
<ProfileForm key={userId} initialName={user.name} />

// 一个约定：以 initial / default 开头的 prop，
// 意思就是"只在初始化时读一次，之后不再跟随"。
Vue · 同样的两种写法
<!-- ❌ 用 watch 同步 -->
<script setup lang="ts">
const props = defineProps<Props>();
const name = ref(props.initialName);
watch(() => props.userId, () => {
  name.value = props.initialName;
});
</script>

<!-- ✅ 让 key 触发重建 -->
<script setup lang="ts">
const props = defineProps<{ initialName: string }>();
const name = ref(props.initialName);
</script>
<template>
  <input v-model="name" />
</template>

<!-- 父组件 -->
<ProfileForm :key="userId" :initial-name="user.name" />
小结
  • state 挂在「树中的位置 + key」上，不挂在组件函数上。
  • 同位置换 props → 保留；换 key → 重建；type 变了 → 重建。
  • 需要"换数据就清空"时，给组件一个 key，别写 effect 去同步。
  • initialXxx 这类命名是在告诉调用者：这个值只读一次。

Chapter 11

Hooks 的规则从何而来

"只能在顶层调用、不能放进 if 里"——这条规则听起来武断。看一眼 React 内部怎么存 Hook 数据，它就变成了唯一可能的设计。

为什么 Hook 不能写在条件里

函数组件没有 this，那 useState 把值存在哪？答案是存在这个组件的 Fiber 节点上， 一个按调用顺序排列的列表。React 不知道你的变量叫什么，它只知道"这是本次渲染的第几个 Hook"。

Vue 为什么没有这条规则

setup() 在组件的一生中只执行一次，ref() 创建的对象直接被局部变量持有——不需要"槽位"， 自然也就没有顺序要求。你完全可以在 if 里 const x = ref(0)。 这一条差异，正是导读那张大图的直接后果。

useEffect：什么时候跑，什么时候清理

原书用四个 Timer 例子演示了依赖数组的三种形态（TimerDemo 无第二参数、TimerOnceDemo 传 []、 TimerConditionalDemo 传 [gameNumber]）。把它们放到同一条时间轴上看，规律一目了然：

    let t = 0;
    const id = setInterval(() => console.log(t++), 1000);
    return () => clearInterval(id);   // ← 必须清理

    <>

        {count}
      </button>
      <button onClick={() => setGameNumber((g) => g + 1)}>
        New Game
      </button>
    </>
  );
}

原书 useZipLookup.js 把"输入邮编 → 查城市州名"的逻辑抽成了自定义 Hook。这是 Hooks 最大的价值： 逻辑复用不再需要 HOC 或 render props。规则很简单——函数名以 use 开头，内部可以调其他 Hook。

export function useZipLookup(zipcode: string) {
  const [address, setAddress] = useState<Address>(null);
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    if (!zipcode) return;
    const ctrl = new AbortController();   // 原书缺这一步
    setLoading(true);
    fetch(`/api/zip/${zipcode}`, { signal: ctrl.signal })
      .then((r) => r.json())
      .then((d) => setAddress({ city: d.City, state: d.State }))
      .catch((e) => { if (e.name !== "AbortError") throw e; })

  }, [zipcode]);

}

import { ref, watch, onWatcherCleanup, type Ref } from "vue";

type Address = { city: string; state: string } | null;

export function useZipLookup(zipcode: Ref<string>) {
  const address = ref<Address>(null);
  const loading = ref(false);

  watch(zipcode, async (zip) => {
    if (!zip) return;
    const ctrl = new AbortController();
    onWatcherCleanup(() => ctrl.abort());
    loading.value = true;
    try {
      const r = await fetch(`/api/zip/${zip}`, { signal: ctrl.signal });
      const d = await r.json();
      address.value = { city: d.City, state: d.State };
    } finally {
      loading.value = false;
    }
  }, { immediate: true });

  return { address, loading };
}
useMemo / useCallback 正在退场

  • Hook 数据按调用顺序存在 Fiber 的槽位里——这就是全部规则的来源。

补 C · 书里没有

大部分 useEffect 都不该存在

上一章讲了 effect 怎么运转。这一节讲更要紧的事：它不该用来做什么。初学者写的 effect 里，大约七成是多余的。

先给判据，一句话：effect 是用来把 React 和它外部的世界对齐的。 网络、浏览器 API、订阅、定时器、第三方库——这些东西 React 管不着，需要你手动同步。 如果一件事的两端都在 React 内部（state 算 state、props 算 state、点击后改 state），那就不需要 effect。

四种常见的多余 effect

为什么"多渲染一次"值得在意

用 effect 算派生值时，React 会先用旧值渲染一次、提交到 DOM、然后跑 effect、再渲染一次。 用户可能看到一帧错误的画面（比如闪过一个空字符串或旧的筛选结果）。 在渲染中直接算则只有一次渲染，永远不会出现中间态。

顺带说清"渲染必须是纯的"

上面所有建议都建立在同一个前提上：组件函数在渲染期间不能有副作用—— 不改外部变量、不改 props、不发请求、不碰 DOM。给定同样的 props 和 state，就要返回同样的结果。 这是并发渲染能中断重来、StrictMode 敢跑两遍、React Compiler 敢自动缓存的共同基础。 开发模式下那次"多余"的重复调用，正是用来帮你发现哪里破坏了这条规则。

小结
  • 判据：effect 用来和 React 之外的世界同步，两端都在内部就不需要它。
  • 用户操作 → 写事件处理器；可推导的值 → 渲染中直接算；props 变了要重置 → 换 key。
  • 用 effect 算派生值会多渲染一次，用户可能看到一帧错误画面。
  • 订阅外部数据源优先用 useSyncExternalStore；取数优先交给数据层库。
  • 渲染必须是纯函数——这是上面一切结论的前提。

两边都捕不到异步错误

  • React 里错误边界仍需 class——直接用 react-error-boundary。
  • Vue 里任何组件加个 onErrorCaptured 就是边界，返回 false 阻止冒泡。
  • 异步错误两边都捕不到，需要单独处理。

上面两段代码只解决了竞态，还没处理缓存、去重、重试、焦点重取、离线。 生产项目直接用数据层库：React 侧是 TanStack Query（原 React Query）或路由的 loader； Vue 侧是 TanStack Query 的 Vue 版或 @vueuse/core 的 useFetch。 原书用的 axios-hooks 已经很少见了。

localStorage：原书 Clicker 系列的坑

Clicker3.js 写的是 useState(Number(localStorage.getItem("counter")) || 0)。 这行代码在每一次渲染都会读一次 localStorage——虽然只有第一次的返回值被采纳，但同步的磁盘读取白白执行了。 正确写法是传函数（惰性初始化）：

// ❌ 每次渲染都执行 getItem
const [count, setCount] = useState(Number(localStorage.getItem("counter")) || 0);

// ✅ 只在首次挂载时执行一次
const [count, setCount] = useState(() => {
  try {
    return Number(localStorage.getItem("counter")) || 0;
  } catch {
    return 0;   // 隐私模式下 localStorage 可能直接抛异常
  }
});

useEffect(() => {
  localStorage.setItem("counter", String(count));
}, [count]);

Vue 侧对应的是 @vueuse/core 的 useLocalStorage("counter", 0)——一行搞定读写同步， 而且跨标签页也会同步。React 侧要做到跨标签页同步，需要 useSyncExternalStore 订阅 storage 事件。

小结
  • effect 里取数必须在清理函数中 abort 或设置忽略标志，否则会有竞态。
  • useState(fn) 传函数才是惰性初始化，传值会每次渲染都计算。
  • 真实项目用 TanStack Query 一类的数据层，别手写缓存与重试。
  • React Router 7 的 loader 能把取数提前到导航阶段，避免加载闪烁。

Context 穿透组件树

原书用同一个 Dashboard 写了三遍：逐层传 props、用 Context、用组合。这三种解法值得放在一起看——因为大多数人只学了第二种。

chapter17/PropDrilling.js · DashboardApp.js · DashboardAppContext.js · DashboardAppComposition.js · contexts/UnitsContext.js
React 19 · UnitsContext.tsx
import { createContext, useContext, useState,
         type ReactNode } from "react";

type Units = {
  lengthUnit: "cm" | "inch";
  tempUnit: "c" | "f";
  setLengthUnit: (u: "cm" | "inch") => void;
  setTempUnit: (u: "c" | "f") => void;
};

const UnitsContext = createContext<Units | null>(null);

export function UnitsProvider({ children }: { children: ReactNode }) {
  const [lengthUnit, setLengthUnit] = useState<"cm" | "inch">("cm");
  const [tempUnit, setTempUnit] = useState<"c" | "f">("c");

  // React 19：Context 本身就是 Provider，不用写 .Provider
  return (
    <UnitsContext value={{ lengthUnit, tempUnit,
                           setLengthUnit, setTempUnit }}>
      {children}
    </UnitsContext>
  );
}

// 自定义 Hook 把"忘了套 Provider"变成明确的报错
export function useUnits() {
  const ctx = useContext(UnitsContext);
  if (!ctx) throw new Error("useUnits 必须在 UnitsProvider 内使用");
  return ctx;
}
Vue 3 · units.ts + provide/inject
import { ref, provide, inject, type InjectionKey, type Ref } from "vue";

type Units = {
  lengthUnit: Ref<"cm" | "inch">;
  tempUnit: Ref<"c" | "f">;
};

// InjectionKey 让 inject 的返回值自动带上类型
export const UnitsKey: InjectionKey<Units> = Symbol("units");

export function provideUnits() {
  const lengthUnit = ref<"cm" | "inch">("cm");
  const tempUnit = ref<"c" | "f">("c");
  provide(UnitsKey, { lengthUnit, tempUnit });
  return { lengthUnit, tempUnit };
}

export function useUnits() {
  const ctx = inject(UnitsKey);
  if (!ctx) throw new Error("useUnits 必须在 provideUnits 之下使用");
  return ctx;
}

// 顶层组件：provideUnits()
// 深层组件：const { lengthUnit } = useUnits();
//
// 注意：Vue 里只有真正读了 lengthUnit.value 的组件才会重渲染，
// 不像 React 那样所有 useContext 的消费者一起重渲染。
Context 的性能陷阱

Context 的 value 一变，所有 useContext 的消费者都会重渲染，无论它们用到的是不是变化的那个字段。 所以：把变化频率不同的数据拆成不同的 Context；value 是对象时注意引用稳定； 需要细粒度订阅时上 Zustand / Jotai 这类状态库。Vue 的 provide/inject 因为传的是 ref，天然是细粒度的。

小结
  • 三种解法的优先级：props → 组合 → Context。
  • React 19 起 <Ctx value> 即可，不用写 .Provider。
  • 用自定义 Hook 包装 useContext，把缺 Provider 变成清晰的错误。
  • Vue 的 provide/inject 传 ref，更新粒度天然更细。

原书清单在做什么

public/index.html 在 #root 之外额外准备了 #sidebar 和 #modal 两个空容器； Modal.js 用 ReactDOM.createPortal(jsx, document.getElementById("modal")) 把弹窗的 DOM 送过去。 对比 ModalWithoutPortal.js 就能看出差别。

React 19 · Modal.tsx
import { createPortal } from "react-dom";
import { useEffect, useRef, type ReactNode } from "react";

export default function Modal({ title, isOpen, onClose, children }: {
  title: string; isOpen: boolean;
  onClose: () => void; children: ReactNode;
}) {
  const dialogRef = useRef<HTMLDialogElement>(null);

  useEffect(() => {
    const d = dialogRef.current;
    if (!d) return;
    if (isOpen) d.showModal();   // 原生 dialog：自带焦点陷阱和 Esc
    else d.close();
  }, [isOpen]);

  return createPortal(
    <dialog ref={dialogRef} onClose={onClose} aria-label={title}>
      <h1>{title}</h1>
      {children}
    </dialog>,
    document.getElementById("modal")!,
  );
}

// 用法：Modal 写在 App 里，DOM 落在 #modal
// <Modal title="…" isOpen={open} onClose={() => setOpen(false)}>
//   <p>…</p>
// </Modal>
Vue 3 · Modal.vue（Teleport）
<script setup lang="ts">
import { ref, watch, useTemplateRef } from "vue";

const props = defineProps<{ title: string; isOpen: boolean }>();
const emit = defineEmits<{ close: [] }>();

const dialog = useTemplateRef<HTMLDialogElement>("dialog");

watch(() => props.isOpen, (open) => {
  open ? dialog.value?.showModal() : dialog.value?.close();
});
</script>

<template>
  <!-- Teleport 就是 Vue 的 Portal，内置指令，无需 import -->
  <Teleport to="#modal">
    <dialog ref="dialog" :aria-label="title" @close="emit('close')">
      <h1>{{ title }}</h1>
      <slot />
    </dialog>
  </Teleport>
</template>
小结
  • Portal / Teleport 只改变 DOM 落点，不改变组件树关系。
  • 因此事件仍沿 React 树冒泡，Context 仍能读到。
  • 典型场景：模态框、Toast、Tooltip、被 overflow 裁切的下拉菜单。
  • 能用原生 <dialog> 就用，它免费送你焦点管理和 Esc 关闭。

Chapter 06

Props 与 State

全书最重要的一章。原书那几个"计数器加两次却只加了一"的例子，暴露的是 React 最反直觉、也最核心的设计：状态是渲染的快照。

chapter06/IncrementTwice.js · IncrementTwiceFixed.js · CounterClass3.js · CounterClass4.js · StoresNearYou*.js · Reminders/ · WelcomeMessage.js

规则一：props 只读，state 私有

propsstate
谁给的父组件组件自己
能不能改不能。组件内改 props 是未定义行为只能通过 setter 改
改了会怎样父组件重新传入新值 → 本组件重渲染触发本组件（及其子树）重渲染
Vue 对应defineProps，同样只读ref / reactive，可直接改

原书 StoresNearYou.js 一路演进到 StoresNearYou8.js，讲的是默认值该写在哪。 今天答案很简单：解构时给默认值——defaultProps 在 React 19 已对函数组件失效。

React 19 · StoresNearYou.tsx
type Props = {
  latitude?: string;
  longitude?: string;
};

// 默认值直接写在解构里，替代 defaultProps
export default function StoresNearYou({
  latitude = "37.3230",
  longitude = "122.0322",
}: Props) {
  return (
    <>
      <div id="map-container">
        <Map latitude={latitude} longitude={longitude} />
      </div>
      <div id="store-list">
        <StoreList latitude={latitude} longitude={longitude} />
      </div>
    </>
  );
}
Vue 3 · StoresNearYou.vue
<script setup lang="ts">
// withDefaults 的现代等价：解构 props 并给默认值
// （Vue 3.5+ 的响应式 props 解构）
const { latitude = "37.3230", longitude = "122.0322" }
  = defineProps<{
      latitude?: string;
      longitude?: string;
    }>();
</script>

<template>
  <div id="map-container">
    <Map :latitude="latitude" :longitude="longitude" />
  </div>
  <div id="store-list">
    <StoreList :latitude="latitude" :longitude="longitude" />
  </div>
</template>
PropTypes 已经没用了

原书 WelcomeMessage.js、Contact.js、DisplayPrimaryColors.js 大量使用 prop-types。 React 19 已经移除了对 Component.propTypes 的读取——写了不报错，但也不校验。 对照表：PropTypes.string → string；.isRequired → 去掉 ?； PropTypes.oneOf(["red","green"]) → "red" | "green"； PropTypes.node → ReactNode；PropTypes.element → ReactElement； PropTypes.func → 写出完整函数签名。类型检查从运行时挪到了编译期，而且更准。

规则二：状态住在哪，决定了数据往哪流

原书的 SearchBox（第 3、8 章都出现）是最小的"状态提升"样本：两个兄弟组件要共享一个搜索词， 于是搜索词被提到它们最近的公共父级。

规则三：状态是这一次渲染的快照

原书 IncrementTwice.js 里，点一次按钮调用了两次 setState({count: this.state.count + 1})， 结果 count 只增加了 1。IncrementTwiceFixed.js 换成函数式更新后才变成 2。 同样地，SetStateAsync.js 在 setState 之后立刻 console.log，打印的是旧值。 这两个现象是同一件事：

React 19 · Counter.tsx
import { useState } from "react";

export default function Counter() {
  const [count, setCount] = useState(0);

  function incrementTwice() {
    // ❌ 只会 +1：两次算的都是同一个 count
    // setCount(count + 1);
    // setCount(count + 1);

    // ✅ +2：把"怎么算"交给 React
    setCount((c) => c + 1);
    setCount((c) => c + 1);

    console.log(count); // 仍是旧值，这是正常的
  }

  return <button onClick={incrementTwice}>{count}</button>;
}
Vue 3 · Counter.vue
<script setup lang="ts">
import { ref, nextTick } from "vue";

const count = ref(0);

async function incrementTwice() {
  count.value++;
  count.value++;          // 直接 +2，无需特殊写法

  console.log(count.value);   // 2 —— 读的是容器当前值
  console.log(document.querySelector("button")?.textContent);
  // 仍是旧的 —— DOM 还没更新

  await nextTick();       // 等这一轮更新刷进 DOM
  console.log(document.querySelector("button")?.textContent); // "2"
}
</script>

<template>
  <button @click="incrementTwice">{{ count }}</button>
</template>
两边都有"异步"，但异步的东西不同

Vue 里 数据是同步的，DOM 更新是异步的（所以有 nextTick）。 React 里 数据本身在本次渲染中就不会变（快照），DOM 更新自然也是之后的事。 把这两句话记牢，90% 的"为什么我拿到的是旧值"就解释清楚了。

不可变更新的常用写法

原书 RemindersClass/App.js 里有一段典型的"改数组中某一项"：

// 改第 index 项的 isComplete —— React 必须造新数组、新对象
setReminders(reminders.map((r, i) =>
  i === index ? { ...r, isComplete } : r
));

// 增：setReminders([...reminders, item]);
// 删：setReminders(reminders.filter((_, i) => i !== index));
// 排序：setReminders([...reminders].sort(cmp));   // 先复制，sort 会改原数组

// 结构很深时，用 useReducer 或者 immer 的 produce()，
// 别手写五层展开运算符。

Vue 对应写法就是 reminders.value[index].isComplete = isComplete——一行。 这是两边最直观的体验差异，也是各自设计取舍最集中的地方。

小结
  • props 只读；默认值写在解构里；类型交给 TypeScript。
  • 状态提升到最近公共父级：数据下行，事件上行。
  • state 是本次渲染的快照：基于旧值算新值时用 setState(prev => …)。
  • 同一事件内的多次 setState 会批处理，只重渲染一次。
  • React 需要不可变更新，Vue 可以就地修改——这是两者所有差异的根。

补 C · 书里没有

大部分 useEffect 都不该存在

上一章讲了 effect 怎么运转。这一节讲更要紧的事：它不该用来做什么。初学者写的 effect 里，大约七成是多余的。

先给判据，一句话：effect 是用来把 React 和它外部的世界对齐的。 网络、浏览器 API、订阅、定时器、第三方库——这些东西 React 管不着，需要你手动同步。 如果一件事的两端都在 React 内部（state 算 state、props 算 state、点击后改 state），那就不需要 effect。

四种常见的多余 effect

❌ 用 effect 算派生值
function Profile({ first, last }: Props) {
  const [full, setFull] = useState("");

  // 多渲染一次：先画出空的，再画出正确的
  useEffect(() => {
    setFull(first + " " + last);
  }, [first, last]);

  return <h1>{full}</h1>;
}

// —— 以及：用 effect 响应点击
function Form() {
  const [submitted, setSubmitted] = useState(false);

  useEffect(() => {
    if (submitted) post(data);   // 逻辑离触发点很远
  }, [submitted]);

  return <button onClick={() => setSubmitted(true)}>
    提交
  </button>;
}
✅ 改掉之后
function Profile({ first, last }: Props) {
  // 渲染时直接算。它本来就不是"状态"
  const full = first + " " + last;
  return <h1>{full}</h1>;
}

// —— 事件就写在事件里
function Form() {
  function handleSubmit() {
    post(data);          // 一眼看到因果
  }
  return <button onClick={handleSubmit}>提交</button>;
}

// —— 筛选列表同理，不要存成 state
function List({ items, query }: Props) {
  const visible = items.filter((i) => i.name.includes(query));
  return <ul>{visible.map((i) =>
    <li key={i.id}>{i.name}</li>)}</ul>;
}
为什么"多渲染一次"值得在意

用 effect 算派生值时，React 会先用旧值渲染一次、提交到 DOM、然后跑 effect、再渲染一次。 用户可能看到一帧错误的画面（比如闪过一个空字符串或旧的筛选结果）。 在渲染中直接算则只有一次渲染，永远不会出现中间态。

那什么才是"外部世界"

React · 这些才需要 effect
// 1. 订阅浏览器事件
useEffect(() => {
  const onResize = () => setWidth(window.innerWidth);
  window.addEventListener("resize", onResize);
  return () => window.removeEventListener("resize", onResize);
}, []);

// 2. 操作 React 管不到的 DOM 属性
useEffect(() => {
  document.title = `(${unread}) 收件箱`;
}, [unread]);

// 3. 接入第三方命令式库
useEffect(() => {
  const map = new MapLib(ref.current!);
  return () => map.destroy();
}, []);

// 4. 网络请求（记得处理竞态，见第 16 章）
//    但实践中更应该交给 TanStack Query 或路由 loader

// 订阅外部数据源的专用 Hook，比 effect 更合适：
const width = useSyncExternalStore(
  (cb) => { window.addEventListener("resize", cb);
            return () => window.removeEventListener("resize", cb); },
  () => window.innerWidth,
  () => 1024,          // 服务端渲染时的兜底值
);
Vue · 同一条界线
<script setup lang="ts">
import { ref, computed, watch, onMounted, onUnmounted } from "vue";

const first = ref("Ada"), last = ref("Lovelace");

// ✅ 派生值用 computed，不要用 watch 写回另一个 ref
const full = computed(() => `${first.value} ${last.value}`);

// ❌ Vue 里对应的反模式长这样：
// const full = ref("");
// watch([first, last], () => { full.value = ... });

// ✅ 外部世界才用生命周期 / watch
const width = ref(window.innerWidth);
const onResize = () => { width.value = window.innerWidth; };
onMounted(() => window.addEventListener("resize", onResize));
onUnmounted(() => window.removeEventListener("resize", onResize));

// 文档标题这类外部状态
watch(unread, (n) => { document.title = `(${n}) 收件箱`; });
</script>
顺带说清"渲染必须是纯的"

上面所有建议都建立在同一个前提上：组件函数在渲染期间不能有副作用—— 不改外部变量、不改 props、不发请求、不碰 DOM。给定同样的 props 和 state，就要返回同样的结果。 这是并发渲染能中断重来、StrictMode 敢跑两遍、React Compiler 敢自动缓存的共同基础。 开发模式下那次"多余"的重复调用，正是用来帮你发现哪里破坏了这条规则。

小结
  • 判据：effect 用来和 React 之外的世界同步，两端都在内部就不需要它。
  • 用户操作 → 写事件处理器；可推导的值 → 渲染中直接算；props 变了要重置 → 换 key。
  • 用 effect 算派生值会多渲染一次，用户可能看到一帧错误画面。
  • 订阅外部数据源优先用 useSyncExternalStore；取数优先交给数据层库。
  • 渲染必须是纯函数——这是上面一切结论的前提。

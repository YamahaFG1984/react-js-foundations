key 与协调算法

上一节的管线停在"协调算出差异"。这一节讲它怎么算——以及为什么 key 写错会让输入框里的内容整体错位一格。

三条规则

React 拿到新旧两棵 Element 树后，不做通用的树 diff（那是 O(n³)），而是靠三条假设把复杂度降到 O(n)：

  1. 只比同一层。跨层级移动节点不会被识别成"移动"，只会是"这边删掉、那边新建"。
  2. 同一位置上 type 变了，整棵子树扔掉重建。div 换成 span、Counter 换成 Timer，里面所有 DOM 和 state 一律销毁。
  3. type 相同时，按 key 配对。没写 key 就按下标配对。配上了就复用那个节点——包括它的 DOM 和 state。

什么时候下标当 key 才是安全的

三个条件同时满足：列表永不重排、只在末尾增删、列表项自身没有状态（纯展示文本）。 留言板按时间追加就符合——所以第 8 章那个例子用 key={i} 没问题。 但只要以后可能加上"删除"或"置顶"，它就会立刻变成 bug。默认给稳定 id，成本低得多。

规则二的另一面：条件渲染会意外销毁子树

React · 同一个组件，被包了一层就重建
// ❌ 两个分支里 <Input/> 所在位置的 type 不同
//    切换 fancy 时，输入框内容会被清空
{fancy
  ? <div className="fancy"><Input /></div>
  : <Input />}

// ✅ 保持结构一致，只换 class —— 节点被复用，内容保留
<div className={fancy ? "fancy" : ""}>
  <Input />
</div>

// 同理，这两个写法的行为完全不同：

// type 相同 → 节点被复用，count 保留
{isA ? <Counter /> : <Counter />}

// key 不同 → 卸载重建，count 归零
{isA ? <Counter key="a" /> : <Counter key="b" />}
Vue · 完全一样的规则
<template>
  <!-- ❌ 两个分支结构不同，切换时 input 内容丢失 -->
  <div v-if="fancy" class="fancy"><Input /></div>
  <Input v-else />

  <!-- ✅ 结构一致 -->
  <div :class="{ fancy }"><Input /></div>

  <!-- Vue 里 v-if / v-else 的同类型元素默认会复用， -->
  <!-- 想强制重建就给不同的 key -->
  <input v-if="isEmail" key="email" placeholder="邮箱" />
  <input v-else key="phone" placeholder="手机号" />
</template>
小结
  • 协调只比同层；type 变了就整棵子树重建；type 相同按 key 配对。
  • key 是数据的身份证：同列表内唯一、跨渲染稳定。默认用后端 id 或 crypto.randomUUID()。
  • 下标当 key 只在"永不重排 + 只在末尾增删 + 项无状态"时安全。
  • 条件渲染时保持两个分支的结构一致，否则子树会被无谓地销毁重建。
